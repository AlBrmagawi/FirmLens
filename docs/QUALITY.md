# Quality assurance and release control

A release passes the documented gates for the supported local research workflow. Passing them does not prove absence of all bugs, vulnerabilities, inaccessible interactions or inaccurate firmware findings. Coverage reports describe which code was exercised, not the percentage of correctness.

## Required gates

| Area | Evidence required |
| --- | --- |
| Source quality | Ruff, formatting, mypy, ESLint, TypeScript, production UI build, generated API types without drift |
| Analysis and API contracts | Python tests for extraction boundaries, redaction, comparison coverage, authentication, persistence, cancellation, CLI exits and provider contracts |
| Browser workflow | Chromium, Firefox and WebKit uploads, analysis, evidence, persistent triage, comparison, reports, keyboard dialogs, upload recovery and narrow screens |
| Accessibility | Axe checks across the application views, browser error checks and manual review of captured desktop/mobile screenshots |
| Real integrations | All seven synthetic formats, prepared Grype intelligence, actual Syft inventory, valid CycloneDX/SARIF exports and reproducible fixtures |
| Data safety | Concurrent idempotency, worker crash recovery, cancellation cleanup and isolated restore with table/artifact/permission comparison |
| Runtime security | Enforced sandbox isolation, dependency audits, secret scans and container advisory policy with verified remediation evidence |
| Distribution | Fresh hosted GitHub Actions build and workflow; no credentials, firmware, database dumps, runtime artifacts or dependencies tracked in Git |
| Optional live AI | Real configured provider, scoped citations, redacted context, failure handling and immutable analyzer results; test doubles alone do not establish this |

The [release record](RELEASE_READINESS.md) is the authority for which gates have actually run. A missing or failed gate must be stated explicitly. Do not infer a hosted result from local tests or report a model response generated by a test double as live AI.

## Advisory policy

`scripts/verify_images.mjs` scans the application, analysis sandbox and database. It retains every package/advisory match and blocks critical, high and unknown-severity matches without verified remediation evidence. Medium and lower matches remain visible for review. `node --test tests/test_image_policy.mjs` exercises the policy's rejection behavior.

Two narrowly scoped dispositions have dedicated checks:

- **CVE-2026-85091:** the zlib backport must have the exact reviewed patch and regression source, matching installed file hashes, a successful negative control during build, and a successful installed-library regression during the image gate. [Backport details](../security/zlib/README.md).
- **GO-2026-4887 / CVE-2026-34040:** the upstream advisory concerns Docker daemon authorization middleware. Grype's recorded production package graph must contain its client dependency and exclude all daemon, API-server and authorization packages. The build must use the pinned patched compiler. The host Docker Engine is a separate operator-maintained boundary; this disposition does not certify the host. [Upstream advisory](https://github.com/moby/moby/security/advisories/GHSA-x744-4wpc-v9h2).

These checks classify retained findings; there is no global ignore list. An unrelated advisory, changed package version, missing receipt, changed installed library or imported daemon package fails the gate. Review dispositions whenever base images, analyzer sources, build scripts or the intelligence database change.

## Release procedure

1. Build images completely before running real firmware or restore checks on a busy Docker engine.
2. Run the documented local checks and the full hosted workflow on the intended source revision.
3. Record actual test counts, image identifiers, intelligence identity, observed coverage and known limits. Preserve previous audit records as history.
4. Inspect the Git diff and scan source/history for secrets before pushing. Never include private backups or raw firmware.
5. Publish a release/tag only after evaluating the recorded gates for its advertised support scope. Live-model quality, ARM64 hardware, production-scale multi-user operation and an independent penetration test are separate claims requiring their own evidence.
